# 06 · 代码审查发现与改进建议

> 本章汇总代码审查发现的问题，按**潜在 Bug / 死代码与占位 / 一致性**三类列出，并给出按优先级排序的改进建议。每条含【现象 / 位置 / 影响 / 建议】。

---

## 一、潜在 Bug

### 1. `list_configs(keys)` 生成非法 SQL 且存在注入风险
- **现象**：`client/AppDataClient.py::list_configs(keys)` 在 `keys` 非空时，直接 `f" config_key in (...)"` 拼接到 `SELECT * FROM client_config` 后——**缺少 `WHERE` 关键字**，且**把值用字符串插值而非参数绑定**。
- **影响**：传 `keys` 时 SQL 语法错误（功能不可用）；若 `keys` 含恶意输入则有注入风险。当前调用方不传 `keys`，所以未暴露。
- **建议**：改为 `WHERE config_key IN (?,?,...)` 并 `prepare_execute` 参数绑定。

### 2. `SystemSettingBackend` 携带 4 个从不触发的信号
- **现象**：`backend/SystemSettingBackend.py` 声明了 `changeImage`/`ocrResultReady`/`copySuccess`/`clearContext` 四个信号，明显是从 `OcrViewBackend` **复制粘贴**而来，从未 emit。
- **影响**：误导阅读者，属死代码。
- **建议**：删除与 OCR 无关的 4 个信号。

### 3. `OcrViewBackend.recognize_image` 覆盖线程引用未清理
- **现象**：每次 `recognize_image` 创建新 `OcrHandler` 并赋给 `self._thread`，**未对上一次线程 `wait()`/清理**。
- **影响**：连续识别时旧线程可能悬空；线程在 `wait()` 前被覆盖引用，潜在生命周期问题。
- **建议**：复用单个工作线程，或在创建前对旧线程 `wait()` 后置空；识别期间禁用触发。

### 4. 主题索引映射错位，“跟随系统”不生效
- **现象**：QML 主题下拉 `["浅色","深色","跟随系统"]` 用索引 `0/1/2` 写 `ForTheme.themeMode`；但 Python `ThemeMode` 枚举是 `Light=0 / Dark=1 / High_Contrast=2 / System=3`。于是“跟随系统”落到 `2=High_Contrast`（渲染为亮色）；`ForTheme` 的 1s 系统主题轮询只在 `themeMode==3` 才响应，永不被触发。
- **影响**：“跟随系统”选项实际表现为亮色，功能名不副实。
- **建议**：统一枚举映射（QML 选择值 ↔ Python `ThemeMode`），把“跟随系统”映射到 `System=3`。

### 5. `env.yml` 日志键名不匹配
- **现象**：代码读取 `log.level`（`_init_logger` 用 `ENV.getprop('log.level', ...)`），而 `env.yml` 写的是 `sys.log_level`。
- **影响**：文件中配置的日志级别**不生效**，回退到默认 `INFO`。
- **建议**：统一为 `log.level`（或让代码读 `sys.log_level`）。

### 6. `ForSettingHelper` 继承 `QSettings` 却绕过其存储
- **现象**：`elements/ForSettingHelper.py` `class ForSettingHelper(QSettings)`，构造传 org/app，但 `value`/`setValue`/`remove` 全被改写为走 `AppDataClient`/DB。
- **影响**：**继承 QSettings 却不使用其存储机制**，继承关系有误导性、语义不清晰；真存储是 SQLite。
- **建议**：改为组合（持有 DB 访问器）而非继承 QSettings，明确数据源。

### 7. 数据库“加密能力”与现状不符
- **现象**：代码/文档暗示加密（`sqlite3x64.dll` + `sqlite3_key`），但以空密码打开，`db/AppData.db` 为明文。
- **影响**：若开发者误以为已加密，密钥（百度 AK/SK）明文落库存在泄露风险。
- **建议**：二选一——要么启用真实加密并设 `appdata.password`；要么移除/降级加密措辞并在文档明确“明文”。

## 三、一致性与小问题

- **双主题体系并存**：`ForTheme`（Python，动态亮/暗）与 `Colors.qml`（QML 静态板）同时存在，页面用 `ForTheme`、`FMenu/FMenuBar` 用 `Colors`，维护易混乱。建议收敛到单一主题源。
- **`typeutis.py` 文件名拼写**：应为 `typeutils`，无实质影响但易误读。
- **`requirements.txt` 编码**：UTF-16 BOM，常见工具解析异常。建议转 UTF-8。
- **`OcrResultModel` 频繁 `beginResetModel/endResetModel`**：结果量大时全量重置有性能开销，可考虑增/改/删差异化更新。
- **`HttpResource` 方法内 `import yaml`**：局部导入风格不统一。
- **`OcrBox` 与 `OcrScene` 内联逻辑重复**：识别框渲染逻辑两处实现，宜抽取复用。

## 四、改进建议（按优先级排序）

**P0 · 正确性与安全**
1. 修复 `AppDataClient.list_configs` 的 SQL 拼接（`WHERE ... IN (?)` + 参数绑定）。
2. 修复 `OcrViewBackend` 线程生命周期（识别期间复用/清理工作线程）。
3. 明确数据库加密状态（启用加密并设密码，或文档标注“明文”）。

**P1 · 功能与一致性**
4. 统一主题枚举映射，让“跟随系统”真正生效。
5. 统一 `env.yml` 日志键名，使日志级别配置生效。
6. 收敛双主题体系（`ForTheme` 为主）。

**P2 · 维护性**
7. 移除/收敛死代码与占位（空 `OcrViewModel`、`AppStore`、`SystemSettingBackend` 冗余信号、未用组件）。
8. `ForSettingHelper` 改为组合而非继承 QSettings。
9. 转 UTF-8 的 `requirements.txt`；修正 `typeutis` 文件名。

**P3 · 工程质量**
10. 补充单元测试：OCR 结果解析、文件复制去重/取消、`as_dataclass`/`asjson`、配置子系统、DB CRUD。
11. 为 OCR 全链路引入集成/冒烟测试，降低百度接口回归风险。

## 小结

当前项目**骨架清晰、可正常运行**，核心亮点是：干净的 QML/Python 桥接、统一的 JSON 跨层数据、自研可加密 SQLite 层、完整的两套热重载与打包链。主要风险集中在**少量 SQL/线程细节**、**主题枚举错位**、以及**加密名实不符**，另有一批**待清理的死代码与占位**。按上述 P0→P3 顺序推进即可在不大幅重构的前提下稳步提升健壮性与可维护性。
